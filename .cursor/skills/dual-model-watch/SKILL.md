# 双模型盯梢（Doer + Watcher）

## 何时必须用

- FY301 / 定位器固件 / HART / 仿真骨架等**不可轻易返工**的任务
- 单模型做完后曾出现：编译不过、逻辑空洞、首页空白、缺测试等
- 要合并进主分支或给客户用的改动

普通小改（改文案、调样式）不必双模型。

## 角色分工

| 角色 | 做什么 | 不做什么 |
|------|--------|----------|
| **做（Doer）** | 按任务实现、自测、给证据 | 不自己「审查通过」收工 |
| **盯（Watcher）** | 对照目标查 bug、缺项、风险假设 | 不重写整单（除非做方失败需接管） |

**禁止**：同一聊天里同一模型又写又宣称审查通过。盯梢必须**新开 Agent** 或走产品内置审查。

## Cursor 里怎么做（推荐顺序）

### A. 默认盯梢（最快，日常重要任务）

1. **做**：Agents Window → New Agent → 选模型 A → 写清验收标准 → 让其做完并自测。
2. **盯**：同一会话或新会话输入 `/agent-review`，重要任务选 **Deep**。
3. 做方按审查意见改；改完再跑一次 Quick review 或让盯方确认「无阻断项」。

### B. 异模型盯梢（更稳，固件级）

1. **做**：模型 A（实现向）完成分支/提交。
2. **盯**：再开一个 Agent → 选**不同**模型 B → 提示词用下面「盯梢提示词」。
3. 盯方只出问题清单与严重级别；做方再修。
4. 上 PR 后可选 Bugbot：`cursor review` / `bugbot run`。

### C. 发现问题后的交流（先对齐出发点，再改；禁止无限改）

Cursor **不会**让两个模型自动开聊；由您传话。但传话内容**首先是立场与理由**，不是甩一堆补丁清单互相砸。

```
1) 对齐（必做，最多 1 轮）
   做方：我按什么目标/约束做的、已知取舍
   盯方：我按什么验收盯的、不同意哪些取舍、为什么
   → 您拍板：本轮范围、以谁为准、哪些不改

2) 有限修改（最多 2 轮）
   只修您批准的阻断项；禁止顺手重构

3) 收工或升级
   无阻断 → 收工
   仍争持 → 您拍板 / 换更强模型做一次 Deep，禁止第 3 轮互撕
```

**硬停（防乱七八糟）**

| 规则 | 说明 |
|------|------|
| 对齐 1 轮 + 修改 ≤ 2 轮 | 超过必须停，由您决定 |
| 只改批准清单 | 未批准的「应修/建议」本轮禁止动 |
| 禁止扩大范围 | 不做无关重构、不换架构「顺便优化」 |
| 争持即升级 | 双方各写 3 行理由 → 您选一边，另一方执行，不再辩论 |

**对齐提示词（先贴给「做」，再贴给「盯」）**

做方：

```text
用 10 行以内说明你的出发点：
1) 任务目标与验收你如何理解
2) 你做了什么、刻意没做什么
3) 关键取舍（为何这样设计）
不要改代码。等盯方与主人拍板后再改。
```

盯方：

```text
先读做方的出发点，再审查。输出：
1) 你同意的出发点
2) 你不同意的点 + 理由（各不超过 3 条）
3) 建议本轮唯一目标（一句话）
4) 若主人批准后才改的阻断项（≤5 条）
不要改代码。不要开打补丁战。
```

您拍板话术（贴给双方）：

```text
本轮拍板：以「…」为准；只修：B1/B2；禁止改：…；修改最多 2 轮后收工。
```

**有限修改时**才用问题清单模板（见下）；清单是执行工具，不是讨论本身。

### D. 不要当成盯梢的

- `/best-of-n`：多模型**竞赛实现**，不是盯梢；只有「要对比多套方案」时用。
- 无上限互传「再改一版」：禁止。那是发散，不是交流。

## 盯梢提示词（复制即用）

```text
你是盯梢审查员，不是实现者。审查当前分支相对 main（或指定 base）的改动。

任务目标：<粘贴原任务验收标准>
已知风险：<例如：单模型曾留下空首页 / 未编译 / 缺测试>

请输出：
1. 阻断项（必须修）：编译/链接、错误逻辑、安全、数据丢失、验收未达标
2. 应修项：缺测试、边界、接口不一致
3. 建议项：可读性/结构
4. 未验证项：你没跑过、缺环境导致无法证明的部分

规则：
- 不要重写整单；最多给最小补丁建议
- 每个问题标明文件路径
- 若无明显阻断，明确写「无阻断项」并列出你实际检查了什么
```

## 问题清单模板（盯 → 做，便于粘贴讨论）

```text
【盯梢问题清单】相对分支: <branch> / base: <main>
阻断项:
- [B1] 文件: <path> — 问题: <一句话> — 建议最小改法: <可选>
应修项:
- [S1] ...
建议项:
- [A1] ...
未验证项:
- [U1] ...
本轮结论: 有阻断 / 无阻断
```

做方回复模板：

```text
【做方回复】
- [B1] 已修：<证据/命令> | 或 不修：<理由>
- [S1] ...
请盯方复检阻断项。
```

## FY301 / 定位器补充

- 固件骨架、HART、仿真任务：默认走 **B（异模型盯梢）** + `/agent-review` Deep。
- 验收至少包含：能编译/能跑通入口、关键模块有桩或实现边界清晰、文档/目录与仓库约定一致。
- 可复用事实写入 `positioner-rd` Skill 与 `AI研发产品/docs/kb/`（镜像 `ValvePositioner/docs/kb`）；增量，勿整篇重写。
- 本机安装：`AI研发产品/docs/kb/install-skills-to-home.ps1` → `~\.cursor\skills\positioner-rd`。

## 收工门槛（盯梢通过才算完成）

- [ ] 做方给出运行/编译/测试证据
- [ ] 盯方（或 `/agent-review` Deep）无**阻断项**
- [ ] 阻断项已修且盯方复检或第二次 review 通过

## 模型配对（经验，可改）

| 做 | 盯 |
|----|----|
| 较快实现模型 | 更强推理/审查模型 |
| Cloud Agent 实现 | 本机另一 Agent 或 Bugbot 盯 PR |

具体型号随 Cursor 可选列表变；原则是 **做 ≠ 盯、模型尽量不同**。
